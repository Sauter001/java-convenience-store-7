## 1. try-catch와 Indent Depth 관리

### 📌 결정 사항
**예외는 Service/Domain 계층에서 throw하고, Controller 계층에서 catch하는 단일 지점 처리 전략**을 채택한다.

### 🤔 문제 상황
try-catch 블록도 indent depth에 포함되므로, 중첩 시 depth 2를 쉽게 초과한다.

```java
// ❌ Bad: depth 초과
public void run() {                    // depth 0
    try {                              // depth 1
        while (true) {                 // depth 2
            try {                      // depth 3 ❌ 초과!
                String input = read();
                if (validate(input)) { // depth 4 ❌❌
                    // ...
                }
            } catch (Exception e) {
                // ...
            }
        }
    } catch (Exception e) {
        // ...
    }
}
```

### ✅ 해결 방안

#### 1) 예외 처리 계층 분리

**Domain/Service Layer**: 예외를 throw만 수행
```java
public class OrderService {
    public Order createOrder(String input) {
        validateFormat(input);      // throw만 함
        validateStock(input);       // throw만 함
        return new Order(input);
    }

    private void validateFormat(String input) {
        if (!input.matches("\\[.+-\\d+\\]")) {
            throw new ServiceException("올바르지 않은 형식으로 입력했습니다. 다시 입력해 주세요.");
        }
    }
}
```

**Controller Layer**: 예외를 catch하여 재시도
```java
public class StoreController {
    public void run() {
        retry(() -> processPurchase());
    }

    private void processPurchase() {
        // 예외를 catch하지 않고 위로 throw
        Order order = orderService.createOrder(inputView.readOrder());
        Receipt receipt = storeService.process(order);
        outputView.printReceipt(receipt);
    }
}
```

#### 2) 메서드 분리로 depth 관리
```java
// try-catch가 있어도 메서드 분리로 depth 2 유지
private void retry(Runnable task) {
    while (true) {              // depth 1
        try {                   // depth 2 ✅
            task.run();
            return;
        } catch (IllegalArgumentException e) {  // depth 2 ✅
            outputView.printError(e.getMessage());
        }
    }
}
```

### 📊 효과
- try-catch 중복 코드 제거
- depth 2 제약 준수
- 예외 처리 로직의 중앙화

## 2. 재시도 메커니즘 설계 (Retry Pattern)

### 📌 결정 사항
**Functional Interface(Runnable, Supplier)를 활용한 재시도 유틸리티 메서드**를 구현한다.

### 🤔 배경
입력 검증 실패 시 재입력 요구사항:
- 잘못된 입력 시 `[ERROR]` 출력 후 재입력
- 여러 입력 지점에서 동일한 재시도 로직 필요

### ✅ 해결 방안

#### 1) 두 가지 오버로드 메서드 제공

**반환값이 없는 경우**: `Runnable` 사용
```java
private void retry(Runnable task) {
    while (true) {
        try {
            task.run();
            return;
        } catch (IllegalArgumentException e) {
            outputView.printError(e.getMessage());
        }
    }
}

// 사용 예시
retry(() -> {
    outputView.printWelcome();
    outputView.printProducts(products);
});
```

**반환값이 있는 경우**: `Supplier<T>` 사용
```java
private <T> T retry(Supplier<T> task) {
    while (true) {
        try {
            return task.get();
        } catch (IllegalArgumentException e) {
            outputView.printError(e.getMessage());
        }
    }
}

// 사용 예시
String input = retry(() -> inputView.readOrder());
Order order = retry(() -> orderService.createOrder(input));
boolean hasMembership = retry(() -> askMembership());
```

#### 2) 중복 제거 최적화 (선택사항)

Runnable 버전에서 Supplier 버전을 재사용:
```java
private void retry(Runnable task) {
    retry(() -> {
        task.run();
        return null;  // 반환값 무시
    });
}

private <T> T retry(Supplier<T> task) {
    while (true) {
        try {
            return task.get();
        } catch (IllegalArgumentException e) {
            outputView.printError(e.getMessage());
        }
    }
}
```

### 🔄 대안 검토

#### 대안 1: Function 사용
```java
// ❌ 부적합: 입력 파라미터가 필요 없음
private <T, R> R retry(Function<T, R> task, T input) { ... }
```
→ 우리 사용 사례에서는 입력이 없으므로 불필요하게 복잡함

#### 대안 2: while-try-catch 직접 작성
```java
// ❌ 중복 코드 발생
private Order readOrder() {
    while (true) {
        try {
            return orderService.create(inputView.read());
        } catch (Exception e) {
            outputView.printError(e.getMessage());
        }
    }
}
// 매 메서드마다 동일 패턴 반복...
```
→ 코드 중복이 많고 depth 관리 어려움

#### 대안 3: Supplier만 사용
```java
// ❌ void 메서드에서 null 반환이 어색함
retry(() -> {
    outputView.print();
    return null;  // 의미 없는 null
});
```
→ 의미론적으로 부자연스러움

### ✅ 최종 선택: Runnable + Supplier 오버로딩
**이유**:
- void 로직에는 `Runnable`이 의미론적으로 명확
- 반환값 필요 시 `Supplier<T>`로 타입 안전성 보장
- Java 타입 추론으로 사용자는 구분 불필요
- 메서드 오버로딩으로 중복 최소화

### 📊 효과
- while-try-catch 패턴 중복 제거
- 재시도 로직의 일관성 확보
- 테스트 용이성 향상 (재시도 로직만 독립 테스트 가능)
- depth 2 제약 준수

## 4. Functional Interface 선택 가이드

### 📌 Java 표준 Functional Interface 정리

| Interface | 메서드 시그니처 | 용도 | 예시 |
|-----------|----------------|------|------|
| `Runnable` | `void run()` | 파라미터 ✗, 반환값 ✗ | `() -> System.out.println("Hi")` |
| `Supplier<T>` | `T get()` | 파라미터 ✗, 반환값 ✓ | `() -> "Hello"` |
| `Consumer<T>` | `void accept(T t)` | 파라미터 ✓, 반환값 ✗ | `(s) -> System.out.println(s)` |
| `Function<T,R>` | `R apply(T t)` | 파라미터 ✓, 반환값 ✓ | `(s) -> s.length()` |
| `Predicate<T>` | `boolean test(T t)` | 파라미터 ✓, boolean 반환 | `(n) -> n > 0` |

### ✅ 선택 기준

**우리 프로젝트의 재시도 패턴**:
- 입력 파라미터 필요 없음 (외부 의존성 주입됨)
- 반환값이 있을 수도, 없을 수도 있음

→ **`Runnable`(void) + `Supplier<T>`(반환값) 조합 선택**

### 📝 사용 예시 정리

```java
// void: Runnable
retry(() -> outputView.printWelcome());

// String: Supplier<String>
String input = retry(() -> inputView.readOrder());

// Order: Supplier<Order>
Order order = retry(() -> orderService.createOrder(input));

// boolean: Supplier<Boolean>
boolean answer = retry(() -> {
    String yn = inputView.readYesNo();
    return parseYesNo(yn);
});

// 메서드 참조도 가능
boolean answer = retry(this::askMembership);
```

## 5. 코드 컨벤션 준수 전략

### 📌 우아한테크코스 제약사항

#### 금지 사항
- ❌ `else` 키워드
- ❌ 삼항 연산자 (`? :`)
- ❌ `switch`/`case`

#### 필수 사항
- ✅ indent depth 최대 2
- ✅ 메서드 길이 최대 10줄
- ✅ Java Enum 적극 활용

### ✅ 대응 방안

#### 1) else 대신 Early Return
```java
// ❌ else 사용
public String getStatus(int stock) {
    if (stock > 0) {
        return stock + "개";
    } else {
        return "재고 없음";
    }
}

// ✅ Early Return
public String getStatus(int stock) {
    if (stock == 0) {
        return "재고 없음";
    }
    return stock + "개";
}
```

#### 2) 삼항 연산자 대신 메서드 분리
```java
// ❌ 삼항 연산자
int discount = hasMembership ? amount * 0.3 : 0;

// ✅ 메서드로 분리
int discount = calculateMembershipDiscount(hasMembership, amount);

private int calculateMembershipDiscount(boolean hasMembership, int amount) {
    if (!hasMembership) {
        return 0;
    }
    return (int) (amount * 0.3);
}
```

#### 3) switch 대신 Enum + 메서드
```java
// ❌ switch/case
public int getDiscount(String type) {
    switch (type) {
        case "MEMBERSHIP": return 8000;
        case "PROMOTION": return 5000;
        default: return 0;
    }
}

// ✅ Enum 활용
public enum DiscountType {
    MEMBERSHIP(8000),
    PROMOTION(5000),
    NONE(0);

    private final int maxAmount;

    DiscountType(int maxAmount) {
        this.maxAmount = maxAmount;
    }

    public int getMaxAmount() {
        return maxAmount;
    }
}
```

## 6. 예외 처리 정책

### 📌 결정 사항
모든 에러 메시지에 `[ERROR]` prefix를 자동으로 추가하는 커스텀 예외 클래스를 사용한다.

### ✅ 구현

```java
public class ServiceException extends IllegalArgumentException {
    public static final String ERROR_PREFIX = "[ERROR] ";

    public ServiceException(String message) {
        super(ERROR_PREFIX + message);
    }
}
```

### 📊 효과
- `[ERROR]` prefix 누락 방지
- 일관된 에러 메시지 형식
- 상수로 관리하여 수정 용이
